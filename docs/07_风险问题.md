## 0. 风险等级定义

| 等级 | 定义 | 处置要求 |
| :--- | :--- | :--- |
| **P0（致命）** | 安全泄露、密钥暴露、主流程不可用、数据损坏 | 立即修复 |
| **P1（严重）** | 功能性 Bug、核心链路静默失败、明显性能缺陷 | 本迭代内修复 |
| **P2（中等）** | 可维护性差、配置漂移、可扩展性受限 | 规划修复 |
| **P3（建议）** | 代码规范、优化空间 | 择机优化 |

**总体结论**：系统架构设计思路清晰（双层索引 + 混合检索 + RRF + Rerank + HyDE + LangGraph 编排 + SSE 流式输出），模块划分与异常体系具备一定工程化基础。但按企业级生产标准衡量，当前存在 **1 项 P0 安全事件（真实密钥已提交仓库）**、**多个会导致主流程运行失败或静默降级的功能性 Bug**、**单进程内存态架构导致的水平扩展能力缺失**，以及测试、日志、配置管理方面的系统性短板。**建议在上线前完成 P0/P1 项整改。**

风险统计：P0 × 5，P1 × 14，P2 × 15，P3 × 10（详见下文）。

  - `MINERU_API_TOKEN=sk-ogduyOv1TxicuLZ77lFMc4ylcUvQ24r3xfRuutTyVOEyh2S7`
  - `MONGO_URL=mongodb://admin:123456@11.0.1.190:27017`（弱口令 + 明文 + 无 TLS）

- **建议**：

### 1.2 【P0】全部 API 无认证、无授权、无租户隔离

- **位置**：`app/rag/import_processor/apis/import_service.py`、`app/rag/query_processor/apis/query_service.py`
- **风险点**：`/upload`、`/query`、`/stream/{session_id}`、`/history/{session_id}`、`/status/{task_id}` 均为匿名可调用；任意人可上传文件触发 GPU 解析任务（DoS / 费用攻击）、读取任意 session_id 的完整对话历史（水平越权，session_id 为可枚举的 UUID 之外的自由字符串）。
- **建议**：引入 JWT/API Key 认证中间件；`session_id`/`task_id` 校验归属；对 `/upload` 增加用户级配额与并发限制。

### 1.3 【P0】上传文件名直接拼接本地路径（路径穿越 / 任意文件写入）

- **位置**：`import_service.py` 上传逻辑：
  ```python
  local_file_path_obj = local_dir_obj / file.filename   # file.filename 完全来自客户端
  with open(import_file_path, "wb") as out_file: ...
  ```
- **风险点**：`file.filename` 形如 `../../evil.py` 或包含绝对路径时，可写出任务目录之外（覆盖任意可写文件）。同时 MinIO 对象名 `pdf_files/YYYYMMDD/{file.filename}` 存在同样的注入面。
- **建议**：使用 `Path(file.filename).name` 仅取纯文件名 + 白名单字符过滤（或直接以 `task_id/uuid` 重命名存储，原始文件名仅作元数据）；校验最终路径 `resolve()` 后必须位于 `data_dir` 之下。

### 1.4 【P0】MinIO 桶策略允许匿名公开读取全部知识库内容

- **位置**：`app/clients/minio_utils.py` `_set_bucket_policy()`：`"Principal": {"AWS": ["*"]}, "Action": ["s3:GetObject"]`
- **风险点**：知识库（企业文档、图片）可被任何能访问 MinIO 端口的人匿名枚举下载；配合 1.1 的默认口令 `minioadmin`，风险进一步放大。
- **建议**：改为预签名 URL（`presigned_get_object`，设置过期时间）供前端按需取图；桶策略收紧为拒绝匿名；MinIO 端口不对公网暴露。

### 1.5 【P1】Milvus 过滤表达式注入 + 转义函数失效 Bug

- **位置**：
  - `app/clients/milvus_utils.py` `escape_milvus_string()` **最后 `return value` 返回了原始值而非转义后的 `s`（第 280 行），转义逻辑完全失效**；
  - `b_node_search_embedding.py` / `c_node_search_embedding_hyde.py`：`expr = f'item_name in {item_names}'` 直接用 Python 列表 f-string，**完全未调用转义**；
  - `e_node_item_name_recognition.py`、`g_node_import_milvus.py` 依赖失效的转义函数拼接 `item_name=="..."` / `file_title=='...'`。
- **风险点**：`item_name` 源自 LLM 输出、`file_title` 源自用户上传的文件名，含 `"`、`'`、`\` 时轻则查询报错，重则被构造恶意 filter（表达式注入）删除/读取非预期数据（`delete(filter=...)` 幂等清理处尤其危险）。
- **建议**：修复 `escape_milvus_string` 返回值；统一封装 `build_in_expr(field, values)` 转义工具；所有 filter 拼接必须经过该工具；对 file_title/item_name 入库前做长度与字符白名单校验。

### 1.6 【P1】ZIP 解压无路径穿越防护（Zip Slip）

- **位置**：`b_node_pdf_to_md.py` `_step_3_download_and_extract()`：`zip_file_obj.extractall(extract_target_dir)`
- **风险点**：MinerU 返回的 ZIP（第三方服务，链路中被劫持或被污染时）内含 `../../` 路径条目可写任意文件。当前依赖外部服务可信度，属供应链风险。
- **建议**：解压前逐条校验 `ZipInfo.filename` 的 `resolve()` 路径必须在目标目录内；限制解压总大小与文件数（防 Zip 炸弹）。

### 1.7 【P1】CORS 全放开 + 允许携带凭据

- **位置**：两个 API 服务的 `CORSMiddleware(allow_origins=["*"], allow_credentials=True, ...)`
- **风险点**：`*` 与 `credentials=True` 组合虽被现代浏览器/CORSMiddleware 规避为回显任意 Origin，等于完全放开跨域凭据访问，为未来接入 Cookie 会话埋雷。
- **建议**：按环境变量配置 Origin 白名单；生产关闭泛域名。

### 1.8 【P2】日志泄露敏感数据

- **位置**：`d_node_document_split.py`（`logger.info(section)` 打印全部切片内容）、`query_service.py`（`logger.info(chunk)` 打印完整状态含答案）、`a_node_item_name_confirm.py`（打印查询与匹配详情）。
- **建议**：生产日志仅输出摘要（长度、数量、ID）；敏感字段脱敏；按等级控制 DEBUG 输出。

### 1.9 【P2】上传无文件类型/大小/数量校验

- **位置**：`import_service.py /upload`
- **风险点**：任意类型文件（含超大文件）先落盘、传 MinIO，后缀校验在 `node_entry` 才做（浪费资源）；无单文件大小上限，可打满磁盘/对象存储。
- **建议**：请求层校验扩展名白名单（pdf/md）、单文件与单请求总大小、文件数上限；上传使用 SpooledTemporaryFile 流式处理。

## 二、正确性缺陷（功能性 Bug）

以下问题经逐行核对源码确认，按对主流程的影响排序。

### 2.1 【P0】`BaseNode` 未初始化 `self.config`，多个导入节点运行即崩

- **位置**：`app/rag/base.py` `__init__` 中 `# self.config = config or get_config()` 被注释；而以下节点均使用 `self.config.*`：
  - `c_node_md_img.py`：`self.config.image_extensions`
  - `d_node_document_split.py`：`self.config.max_content_length` / `min_content_length`
  - `e_node_item_name_recognition.py`：`self.config.item_name_chunk_k` / `item_name_chunk_size`
- **影响**：`AttributeError: 'NodeMDImg' object has no attribute 'config'`，**导入主流程（PDF/MD → 切片 → 入库）当前无法端到端跑通**。
- **建议**：在 `BaseNode.__init__` 中恢复 `self.config = get_config()`（`rag/import_processor/config.py` 已提供单例），并补一个最小导入链路集成测试防止回归。

### 2.2 【P0】`escape_milvus_string` 返回原始值（转义失效）

见 1.5，此处为代码级缺陷本体：`milvus_utils.py:261-280` 函数体完成转义后 `return value`。修复为 `return s` 并补单元测试（含引号、反斜杠、换行、None 入参）。

### 2.3 【P1】MongoDB 历史查询取的是"最旧 N 条"而非"最近 N 条"

- **位置**：`app/clients/mongo_history_utils.py` `get_recent_messages()`：
  ```python
  cursor = mongo_tool.chat_message.find(query).sort("ts", ASCENDING).limit(limit)
  ```
- **影响**：多轮对话上下文永远取会话最早的消息，指代消解与问题改写（`a_node_item_name_confirm`）基于错误历史，随对话变长效果持续劣化。
- **建议**：先 `sort("ts", DESCENDING).limit(n)` 取最近 N 条，再在内存中反转为正序。

### 2.4 【P1】历史消息 `_id` 字段名不匹配，商品名回填功能整体失效

- **位置**：`get_recent_messages` 返回键为 `"id"`；而 `a_node_item_name_confirm.py` `_step_7_check_confirmation` 读取 `msg.get("_id")` → 永远为 `None`，`ids_to_update` 恒空，`update_message_item_names` 从不生效。
- **建议**：统一字段名（推荐 `"id"`），并为该链路补单测。

### 2.5 【P1】`hyde_doc` 未定义在 State Schema，LangGraph 合法性校验会拒绝该更新

- **位置**：`c_node_search_embedding_hyde.py` 返回 `{"hyde_embedding_chunks": res, "hyde_doc": hyde_doc}`；`query_processor/state.py` 的 `QueryGraphState`（`total=True`）没有 `hyde_doc` 字段。
- **影响**：LangGraph 对未声明 channel 的更新会抛 `InvalidUpdateError`，HyDE 分支（即正常检索主路径）执行到该节点即失败。
- **建议**：在 `QueryGraphState` 中补充 `hyde_doc: str` 声明，或从返回值中移除该字段。

### 2.6 【P1】`logger.waring` 拼写错误 → AttributeError

- **位置**：`b_node_pdf_to_md.py:65`：`logger.waring(f"file_dir is none,...")`
- **影响**：当 `file_dir` 缺失时，本应抛出的 `StateFieldError` 变成 `AttributeError`，错误信息失真。
- **建议**：改为 `logger.warning`；全仓 grep 排查类似拼写问题。

### 2.7 【P1】`logger.info("MCP 搜索结果:", docs)` 多余位置参数 → 联网搜索一有结果即崩溃

- **位置**：`d_node_web_search_mcp.py:41`
- **影响**：loguru 对"消息无占位符但传入额外位置参数"会抛异常；即 MCP 搜索成功返回结果时节点必然异常（被 BaseNode 包装为流程失败），搜索失败反而"正常"。**联网搜索功能实际不可用。**
- **建议**：改为 `logger.info(f"MCP 搜索结果: {docs}")`。

### 2.8 【P1】Rerank 异常分支返回畸形数据结构

- **位置**：`f_node_rerank.py:110`：`return [{**merged_multi_docs, "score": None}]`
- **影响**：对 **list** 做 `**` 展开得到 `{0: doc0, 1: doc1, ..., "score": None}` 的单个字典——下游 `_format_reranked_docs` 中 `doc.get("content")` 返回 `None`，prompt 参考内容为空，答案质量塌陷且无告警。
- **建议**：异常时返回 `[{**doc, "score": None} for doc in merged_multi_docs]` 或直接抛给统一错误处理；同时记录 metrics 告警 rerank 失败率。

### 2.9 【P1】`query_config` 阈值未做类型转换，配置了环境变量即运行时崩溃

- **位置**：`query_processor/config.py`：`os.getenv("QUERY_HIGH_LIKE", 0.65)` 等——一旦环境变量存在，值是**字符串**。
- **影响**：
  - `m.get("score", 0) > query_config.query_high_threshold` → `TypeError: '>' not supported between 'float' and 'str'`；
  - `min(query_config.rerank_max_topk, len(ranked_docs))` → `str` 与 `int` 比较同样报错。
- **附注**：`query_mid_threshold` 误用变量名 `QUERY_HIGH_LIKE`（本应 `QUERY_MID_LIKE`），两个阈值同源。
- **建议**：统一 `float(os.getenv(...))` / `int(os.getenv(...))` 包装并给默认值；修正 mid 阈值变量名；启动时做配置校验（fail-fast）。

### 2.10 【P1】`update_task_status` 第三参数语义误用

- **位置**：`query_service.py:103`：`update_task_status(session_id, TASK_STATUS_PROCESSING, is_stream)` —— 签名为 `(task_id, status_name, push_queue: bool)`，`is_stream` 被当作 `push_queue`。
- **影响**：非流式查询（`is_stream=False`）恰好安全；流式查询在 SSE 队列已创建时行为"碰巧正确"，但语义混乱，重构极易引入回归。
- **建议**：改用具名参数 `push_queue=is_stream`，或封装独立的 `notify_status()`。

### 2.11 【P1】非流式 `/query` 在 async 处理函数中同步执行全流程，阻塞事件循环

- **位置**：`query_service.py:83`：`run_query_graph(session_id, user_query, is_stream)`（同步函数，内含 GPU 向量化 + 多次 LLM 调用 + Milvus 检索）
- **影响**：非流式请求期间**整个 FastAPI 事件循环被挂起**（可达数十秒），所有并发请求（含 `/health`、SSE 心跳）全部无响应。
- **建议**：`await asyncio.to_thread(run_query_graph, ...)` 或改为后台任务 + 轮询（与流式路径统一）。

### 2.12 【P1】`reranker_http_utils.py` 缺 `import dashscope` 且与 `lm/reranker_utils.py` 重复

- **位置**：`app/utils/reranker_http_utils.py:11` 直接使用 `dashscope.` 未导入 → 调用即 `NameError`。该文件与 `lm/reranker_utils.rerank_documents` 功能完全重复。
- **建议**：删除重复文件，保留单一实现（见 4.4 本地/在线 rerank 双实现问题）。

### 2.13 【P2】`lifespan.py` 引用不存在的模块，属死代码且误导

- **位置**：`app/core/lifespan.py` 导入 `fileserver_client_manager`、`kubernetes_client_manager`、`mysql_client_manager`（`clients/` 目录下均不存在）。
- **影响**：该文件一旦被引用即 `ImportError`；实际两个 API 服务均未注册 lifespan，**Milvus/MinIO/Mongo 连接无优雅关闭，后台任务无取消机制**。
- **建议**：删除或重写 lifespan 为真实资源初始化/释放（模型、DB 连接、线程池），并在 FastAPI 启动时做依赖健康检查（fail-fast）。

## 三、系统架构与可扩展性

### 3.1 【P1】任务状态与 SSE 队列均为单进程内存态，无法水平扩展

- **位置**：`app/utils/task_utils.py`（`_tasks_*` 模块级字典）、`app/utils/sse_utils.py`（`_session_stream` 字典）
- **影响**：
  1. 多 worker / 多副本部署时，`/status/{task_id}`、`/stream/{session_id}` 请求路由到非处理进程即查不到状态（失败）；
  2. 进程重启，全部进行中任务与 SSE 连接丢失，无恢复能力；
  3. uvicorn `--workers N` 直接不可用。
- **建议**（按改造成本递增）：
  - 短期：明确单进程部署约束 + 前置粘性网关；
  - 中期：任务状态落 Redis（TTL 自动过期），SSE 改 Redis Pub/Sub 广播；
  - 长期：导入链路改 Celery/Arq 任务队列，查询链路状态外置。

### 3.2 【P2】内存态字典无 TTL、无上限 → 内存泄漏

- **位置**：`task_utils.py`（`clear_task` 仅在同 session 再次查询时触发；导入任务从不清理）；`sse_utils.py`（流式 `/query` 创建队列后，若客户端始终不连 `/stream`，队列与积压消息永不释放）。
- **建议**：任务完成/超时后延迟清理（`asyncio.call_later` 或定时扫描）；SSE 队列设创建超时与 `maxsize`；增加活跃任务数指标监控。

### 3.3 【P2】单例客户端均无线程安全保护

- **位置**：`milvus_utils.get_milvus_client`、`minio_utils.get_minio_client`、`lm_utils._llm_client_cache`、`embedding_utils.get_bge_m3_ef`、`reranker_utils.get_reranker_model`
- **影响**：FastAPI BackgroundTasks（线程池）并发首次调用时可能重复初始化（模型重复加载显存翻倍、连接泄漏）；导入多文件并发时概率不低。
- **建议**：统一 `threading.Lock` 双检锁封装；或在应用启动阶段（lifespan）预热完成所有单例。

### 3.4 【P2】导入与查询为两个独立进程（端口 8000/8001），但共享代码导入根不统一

- **位置**：`import_processor` 链路使用 `from rag.xxx import`、`from clients.xxx import`、`from conf.xxx import`；`query_processor` 与 `query_service` 使用 `from app.rag.xxx`、`from app.utils`；`base.py` 用 `from core.logger import logger`，`b_node` 用 `from app.core.logger import logger`。
- **影响**：导入是否成功强依赖 `sys.path`（工作目录/启动方式），"从 IDE 启动"与"命令行启动"行为不一致，隐性脆弱。
- **建议**：全仓统一绝对导入 `app.*`；`pyproject.toml` 配置 `[tool.setuptools.packages.find]` 或以 `python -m app.rag...` 方式启动；用 ruff/isort 固化导入规范。

### 3.5 【P2】阻塞式节点 + GPU 单卡，天然串行瓶颈

- **影响**：所有节点均为同步阻塞实现；BGE-M3 与 BGE-Reranker 同卡（`cuda:0`）加载时导入向量化与查询重排互相争抢显存。
- **建议**：embedding/rerank 独立为推理服务（如 vLLM/TEI 或自建 FastAPI+batch），主服务走 HTTP 调用；查询链路三路召回（向量/HyDE/联网）当前虽是图并行，但**同步节点在线程池中受默认线程数限制**，且每次请求新建 MCP 连接（见 5.3）。

### 3.6 【P3】可扩展性正向设计（保留项）

双层索引（文档级 `kb_item_names` 一级筛选 + 切片级 `kb_chunks` 精准匹配）、混合稠密/稀疏检索、RRF 融合、断崖截断动态 TopK 的设计符合企业级 RAG 最佳实践方向，架构骨架值得保留，上述问题多为实现层缺陷。

## 四、数据处理流程（导入链路）

### 4.1 【P1】切分参数默认值过小且无重叠，损害检索质量

- **位置**：`rag/import_processor/config.py`：`max_content_length=500`（注释自荐 2000）、`min_content_length=200`（自荐 500）；`d_node` 中 `chunk_overlap=0`。
- **影响**：切片过碎导致语义不完整、上下文不足；零重叠导致边界信息丢失，召回质量系统性下降。
- **建议**：默认值对齐推荐值（2000/500）并以 A/B 评估验证；`chunk_overlap` 设为切片长度的 10%~15%；将参数暴露为环境变量。

### 4.2 【P2】幂等清理与插入非原子，失败会产生"半删除"状态

- **位置**：`g_node_import_milvus.py`：先 `delete(filter=file_title==...)` 后 `insert(...)`，两步之间失败 → 旧数据已删、新数据未入，知识库静默缺数据。
- **建议**：以 `batch`/`partition` 版本号方式写入后切换（蓝绿写入）；或失败时记录补偿任务；至少将"删除成功但插入失败"升级为任务 failed 并告警。

### 4.3 【P2】入库字段长度校验缺失

- **位置**：`g_node`/`e_node` 建表 `title/parent_title/file_title/item_name max_length=100`，但切分产物 `title` 为"标题_序号"、`item_name` 为 LLM 自由输出，超长即插入失败；`part` 为 INT8（>127 溢出）；`.env` 中 `EMBEDDING_DIM=1536` 与 BGE-M3 实际 1024 维不一致（配置漂移）。
- **建议**：入库前统一截断/校验各字段长度；`part` 改 INT32；修正 `.env` 注释与默认值，启动时校验 embedding 维度与集合 schema 一致。

### 4.4 【P2】Rerank 本地/在线双实现，默认走在线且无降级

- **位置**：`lm/reranker_utils.py` 同时提供本地 FlagReranker（`compute_score`，实际未被调用，模型仍会被 `get_reranker_model` 按需加载占用显存）与 DashScope 在线 `rerank_documents`（`f_node` 实际使用）；`utils/reranker_http_utils.py` 又是一份损坏副本。
- **影响**：查询链路强依赖外部 API（网络抖动即触发 2.8 的畸形降级）；本地模型白占显存；三份实现漂移。
- **建议**：收敛为单一 rerank 适配层，支持 `local/online` 配置切换与失败重试 + 降级（降级时直接用 RRF 分数并记录告警）。

### 4.5 【P2】MinerU 外调健壮性不足

- **位置**：`b_node_pdf_to_md.py`：`requests.post(url, ...)`（获取上传链接）、`requests.put(signed_url, ...)`、`requests.get(zip_url)` **均未设 timeout** → 第三方服务无响应时线程无限挂起（任务永远 processing）；超时 600s/轮询 3s 硬编码。
- **建议**：所有外调设 `(connect_timeout, read_timeout)` 并加有限重试；超时/轮询参数进配置；外调失败计入任务错误信息（见 7.1）。

### 4.6 【P3】图片摘要速率限制器为局部 deque 且同步 sleep

- **位置**：`c_node_md_img.py` `request_deque` 在每次节点调用内新建（跨文档/跨任务不共享，多文件并发导入时限流失效）；`apply_api_rate_limit` 用 `time.sleep` 阻塞线程；硬编码 `max_requests=10` 与 config `requests_per_minute=15` 漂移。
- **建议**：限流器提为进程级单例（或 Redis 令牌桶）；用 `asyncio.sleep`/线程友好等待；参数从 config 读取。

### 4.7 【P3】切分结果备份写入本地而非对象存储

- **位置**：`d_node` `_step_6_backup` 写 `chunks.json` 到本地目录，随磁盘清理丢失；`output_files/` 已堆积 779 个文件（含 679 张图片）无清理策略。
- **建议**：中间产物归档 MinIO 并设生命周期规则；本地临时目录任务完成后定时清理。

### 4.8 【P3】`TRANSFORMERS_OFFLINE=1` 在模块级强制设置

- **位置**：`lm/embedding_utils.py:9`
- **影响**：新环境（模型缓存为空）首次启动必然失败且报错隐晦；也剥夺了按环境切换在线/离线的能力。
- **建议**：移至 `.env` 由部署侧控制；启动时校验模型路径存在性并给出明确错误。

## 五、查询链路与检索质量

### 5.1 【P1】Milvus `item_name in [...]` 表达式构造不规范

- **位置**：`b_node`/`c_node`：`expr = f'item_name in {item_names}'`
- **影响**：Python 列表字符串化产生单引号字面量 `['A', 'B']`；Milvus 表达式规范要求双引号字符串（单引号兼容性依赖版本）；且值未转义（见 1.5）。含特殊字符的商品名会导致检索报错 → 节点 catch 后返回 `{}`，**用户端表现为"检索不到任何内容但无报错"**。
- **建议**：`expr = 'item_name in [' + ', '.join(f'"{escape_milvus_string(v)}"' for v in item_names) + ']'`，封装为工具函数并单测。

### 5.2 【P2】检索失败被静默吞掉，端到端无告警

- **位置**：`b_node`/`c_node` 的 `except: logger.exception(...); return {}`。
- **影响**：Milvus 宕机时系统仍"正常"返回 LLM 无证据生成的答案（幻觉放大），用户与运维均无感知。
- **建议**：区分"检索结果为空"与"检索系统异常"两类状态；异常时在 state 标记 `retrieval_degraded=True`，答案前缀提示"知识库暂不可用"，并触发告警指标。

### 5.3 【P2】联网搜索节点每次请求新建 MCP 连接，且 `asyncio.run` 有隐患

- **位置**：`d_node_web_search_mcp.py`：每次 `process` 都 `MCPServerStreamableHttp(...)` 建连、`asyncio.run(...)` 驱动。
- **影响**：连接建立开销叠加在用户延迟上；`asyncio.run` 在已有事件循环的线程中会抛 `RuntimeError`，与执行模型强耦合；搜索结果无缓存，相同问题重复外呼（费用）。
- **建议**：进程级复用 MCP 客户端；web 搜索结果按 query 做短 TTL 缓存；考虑加"仅当本地检索置信度不足时才联网"的开关策略（当前无条件三路并发）。

### 5.4 【P2】主体确认策略：高分匹配全量确认，检索范围发散

- **位置**：`a_node` `_step_6_align_item_names`：当前生效逻辑为"所有 score>阈值的匹配全部加入 confirmed"（原"仅一条/择优"逻辑被注释）。
- **影响**：模糊问题（如"华为P60"）可能同时确认多个型号，检索过滤 `item_name in [...]` 范围过大，精度下降——与该节点"收敛主体"的设计目标相悖。
- **建议**：恢复"唯一高分直接确认 / 多条高分取与提取名一致或最高分"策略；候选确认阈值与策略参数化并用评估集验证。

### 5.5 【P3】HyDE 无开关与质量护栏

- 每次查询固定增加一次 LLM 调用（延迟与成本 +30% 量级）；HyDE 文档质量无校验（空/超长/偏题时直接拼接检索）。建议：配置开关、失败时回退普通向量检索、对 hyde_doc 做长度截断。

### 5.6 【P3】答案无引用溯源与幻觉控制机制

- `answer_out.prompt` 仅口头要求"不要编造"；`reranked_docs` 的 `chunk_id/url` 元数据虽进入 prompt，但未做答案内引用标号校验、未接入忠实度在线检测。
- **建议**：要求答案携带 `[n]` 引用并校验 n 的有效性；接入 RAGAS 忠实度抽检（已有离线评估基础 `eval/eval.py`）；prompt 中加入"参考内容不足时明确说明"的兜底指令。

## 六、模型集成与性能瓶颈

### 6.1 【P1】非流式查询阻塞事件循环（同 2.11，性能视角）

GPU 向量化（BGE-M3 `cuda:0`）+ 3 次 LLM 调用（改写/主体识别 + HyDE + 生成）+ Milvus 检索 + DashScope rerank 全部同步串行，单请求 P95 预估 >10s，期间服务完全不可用。**优先修复。**

### 6.2 【P2】Embedding 无批大小/序列长度治理

- **位置**：`f_node` 批次 5 硬编码（config `embedding_batch_size=8` 未使用，漂移）；`generate_embeddings` 不做 token 截断（BGE-M3 上限 8192 token），异常长切片会拖慢整批甚至 OOM。
- **建议**：批次大小读配置并按显存压测调优；入库前按 token 数预截断；`generate_embeddings` 增加失败分批重试。

### 6.3 【P2】LLM 调用无超时/重试/熔断

- **位置**：`lm_utils.get_llm_client` 创建的 `ChatOpenAI` 未配置 `timeout`、`max_retries`；各节点 invoke 失败多为"兜底返回默认值"（如 item_name 回退 file_title）。
- **影响**：上游模型服务抖动时整条链路延迟不可控；兜底掩盖故障（识别失败的商品名退化为文件名，向量与检索语义错位）。
- **建议**：`ChatOpenAI(timeout=..., max_retries=3)`；关键调用（改写、生成）失败显式抛错而非静默兜底；接入熔断（如连续失败降级关闭 HyDE）。

### 6.4 【P3】每次查询新建 `KBQueryWorkflowV2` 并重复编译图

- **位置**：`query_service.run_query_graph`：`workflow = KBQueryWorkflowV2()` 每请求新建+编译（LangGraph 编译有可观测开销）。
- **建议**：模块级单例复用编译产物（LangGraph 编译后图可并发 invoke）。

### 6.5 【P3】SSE 实现的线程占用问题

- **位置**：`sse_utils.sse_generator`：每条消息 `run_in_executor(None, queue.get, True, 1.0)`——每个 SSE 连接长期占用一个默认线程池线程 + 1s 轮询断连检测；无心跳注释事件，中间代理（Nginx）易超时掐断。
- **建议**：改 `asyncio.Queue` + `asyncio.wait_for`（全程无协程阻塞）；每 15~30s 发送 `: ping\n\n` 心跳；为队列设置 `maxsize` 防积压。

## 七、错误处理与容错

### 7.1 【P2】导入任务失败信息不落地，前端只见 "failed"

- **位置**：`import_service.run_graph_task`：异常仅 `logger.info(...)`（级别还用了 info 而非 error），未调用 `set_task_result(task_id, "error", ...)`。
- **建议**：错误消息与节点名写入任务结果并随 `/status` 返回；失败日志级别改 error；为任务增加 `failed_reason` 字段。

### 7.2 【P2】异常处理风格不一，错误被过度吞噬

- 导入侧：`BaseNode.__call__` 把一切异常包成 `ImportProcessError`（原始类型丢失，`node_name` 之外的上下文不足）；
- 查询侧：各节点自行 try/except 返回 `{}` 或默认值（见 5.2），`_summarize_image` 失败静默返回"图片描述"。
- **建议**：统一错误处理策略——基础设施错误（DB/网络）抛出并告警；业务可降级错误显式标记降级原因进 state；保留原始异常链（`raise ... from e` 已部分做到）。

### 7.3 【P2】MinIO 上传失败仅告警继续，造成存储与索引不一致

- **位置**：`import_service` 上传原始文件失败继续流程；`c_node` 图片上传失败仅丢弃该图（MD 中引用仍为本地路径或被跳过）。
- **建议**：原始文件上传失败应标记任务状态为"部分成功"并计入待补偿队列；图片失败时在 MD 中保留占位说明而非静默丢失。

### 7.4 【P3】健康检查接口形同虚设

- `/health` 仅返回 `{"ok": true}`，不探测 Milvus/Mongo/MinIO/模型可用性。
- **建议**：实现分级健康检查（liveness 只查进程；readiness 探测各依赖），供 K8s 探针与网关摘流使用（`deploy/k8s` 已存在，需对齐）。

## 八、日志与可观测性

### 8.1 【P2】`fix_log_position` 每条日志遍历调用栈，性能损耗显著

- **位置**：`core/logger.py`：`logger.patch(fix_log_position)` 中 `inspect.stack()` 对**每条日志**执行全栈扫描（含 enqueue 线程），高频日志（切分节点逐条 INFO）下开销可观。
- **建议**：loguru 原生 `logger.add(..., backtrace=False)` + 依靠 `{name}/{function}:{line}` 字段即可；删除自定义 patch 或仅对 DEBUG 级别启用。

### 8.2 【P2】日志体系分裂：loguru / logging / print 三套并存

- **位置**：`mongo_history_utils.py` 全文用标准 `logging`（未配置 handler，默认 WARNING 以上才输出且格式不统一）；`sse_utils.py`、`g_node`、`import_service` 部分路径用 `print`；文件日志格式 `LOG_FORMAT` 与控制台 `LOG_FORMAT_REQUEST_ID` 不一致（**文件日志丢失 request_id**）。
- **建议**：统一 loguru 单一入口（可为第三方库配 InterceptHandler）；文件日志同样携带 request_id；清除全部 print。

### 8.3 【P2】文件日志 `diagnose=True` 有泄露风险

- **位置**：`core/logger.py:57`：`diagnose=True` 会在异常日志中输出变量值（可能含密钥、用户数据）。
- **建议**：生产环境 `diagnose=False`（用环境区分）。

### 8.4 【P3】无结构化指标与链路追踪

- 现状：只有文本日志；无请求级耗时指标（各节点耗时仅在 `log_decorator` 文本中，而查询节点实际未挂该装饰器）、无召回/延迟/QPS 监控、无 trace_id 贯穿（request_id 默认 "1" 且未见中间件赋值）。
- **建议**：接入 Prometheus 指标（节点耗时直方图、检索命中率、LLM 失败率、rerank 降级次数）；FastAPI 中间件生成 request_id 并写入 `request_id_ctx_var`（当前 contextvar 已建但无生产者）；考虑 OpenTelemetry 贯穿 LangGraph 节点。

## 九、测试覆盖与质量保障

### 9.1 【P1】零自动化测试：核心缺陷无一能被现有"测试"拦截

- **现状**：`pymodules/tests/` 与各文件 `__main__` 块均为**手工冒烟脚本**（需真实 GPU/外网/数据库，无断言、无 pytest 组织、无 CI）；`tests/langgraph/nodes` 为半成品。上述 2.1~2.9 全部缺陷均属"一条单元测试即可拦截"级别。
- **建议**（按性价比排序）：
  1. 为纯函数补 pytest 单测：`escape_milvus_string`、`_rrf_merge`、`_cliff_cutoff`、`_split_long_section`/`_merge_short_sections`、`protect_tables`、`apply_api_rate_limit`、`get_recent_messages`（用 mongomock/fakeredis 思路隔离）；
  2. Mock 外部依赖（LLM/Milvus/MinIO）的节点级测试，重点覆盖异常分支（rerank 失败、检索失败、JSON 解析失败）；
  3. 用 docker-compose（`deploy/` 已有基础）拉起 Milvus/Mongo/MinIO 做导入→查询端到端冒烟，纳入 CI；
  4. `eval/eval.py` + `qa.csv`（RAGAS）作为检索/生成质量回归门禁，扩展题集规模并固化到流水线。

### 9.2 【P3】评估数据与流程问题

- `qa.csv` 规模小、无分层（简单/困难/边界）；eval 结果 CSV 与代码同目录提交（含生成内容，注意脱敏）；eval 依赖 `main_graph`（注释写 v1 `query_app`）与现行 v2 入口可能脱节。
- **建议**：评估集按能力维度分层并版本化；评估脚本与生产入口共用同一 workflow 构造函数，防止"评的不是线上跑的"。

### 9.3 【P3】依赖锁定与运行环境

- `pyproject.toml` 版本下限宽松（`>=`）+ `uv.lock` 存在，尚可；但 `torch>=2.11` 等大版本漂移风险高，且项目要求 Python>=3.12 而 `.env` 路径硬编码 `D:/`，说明仅在一台 Windows 开发机验证过。建议增加 Linux 容器化验证（deploy 已有 compose，需补 RAG 服务自身镜像）。

## 十、配置管理与工程规范

### 10.1 【P2】配置三处定义、互相漂移

- 同一配置在 `app/conf/*.py`、`rag/import_processor/config.py`、`rag/query_processor/config.py`、`.env` 四层重复出现（Milvus、MinIO、LLM key 等），已经出现：`requests_per_minute=15` vs 代码 10、`embedding_batch_size=8` vs 代码 5、`EMBEDDING_DIM=1536` vs 实际 1024、`item_name_chunk_k` 等仅 config 有而 BaseNode 断链。
- **建议**：收敛为单一 Pydantic `Settings`（BaseSettings，`env_file` 统一加载、启动时校验类型与取值范围、失败即拒绝启动）；各流程 config 只保留流程专属参数。

### 10.3 【P2】`load_dotenv()` 散布于 10+ 个模块

- 每个配置文件都调用一次（幂等但混乱），且 `path_util.get_project_root(".env")` 用"存在 .env 文件"推断项目根——一旦上级目录恰有 `.env` 会定位错根。
- **建议**：仅在进程入口（uvicorn 启动器）加载一次；项目根通过 `PROJECT_ROOT` 环境变量或包安装方式确定。

### 10.3 【P3】代码规范问题清单

| 类别 | 示例位置 | 问题 |
| :--- | :--- | :--- |
| 调试残留 | `g_node`（print/sys.modules）、`sse_utils`（多处 print）、`a_node`（大段注释代码） | 上线前清理 |
| 命名 | `b_node` `bactch_id`、`_step_4_write_history(seld, ...)`（self 拼错）、`f_node` `conten` | 拼写错误 |
