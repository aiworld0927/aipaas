## 2. 系统全貌 & 模块总览

### 2.1 全部模块清单

编排拆分为两个文件，通过 `include` 合并为一个 Compose 项目（共 15 个服务）：

- **基础编排 `docker-compose-base.yaml`**（6 个）：init-volumes（一次性预创建中间件数据目录，bind mount 到 `${DOCKER_VOLUME_DIRECTORY:-.}/volumes`）+ etcd / minio / milvus / attu / mongodb
- **主编排 `docker-compose.yaml`**（9 个）：`include` 基础编排，新增 init-app-dirs（一次性预创建应用日志目录 `logs/{svc-ingest,svc-query}`）+ postgres / redis / nacos / rocketmq / svc-ingest / svc-query / frontend（平台中间件数据使用命名卷 pg-data / redis-data / nacos-data / rocketmq-*-data）

#### 基础编排（docker-compose-base.yaml，6 个）

| 模块 | 容器名 | 宿主机端口 | 内部端口 | 说明 |
|------|--------|-----------|---------|------|
| **init-volumes** | aipaas-init-volumes | — | — | 一次性初始化：预创建中间件数据目录并统一属主 |
| **etcd** | milvus-etcd | — | 2379 | Milvus 元数据存储 |
| **minio** | milvus-minio | 9000 / 9001 | 9000 / 9001 | 对象存储（S3 兼容）|
| **milvus** | milvus-standalone | 19530 / 9091 | 19530 / 9091 | 向量数据库 |
| **attu** | attu | 3000 | 3000 | Milvus 可视化管理界面 |
| **mongodb** | mongodb | 27017 | 27017 | 文档存储 |

#### 主编排（docker-compose.yaml，9 个）

| 模块 | 容器名 | 宿主机端口 | 内部端口 | 说明 |
|------|--------|-----------|---------|------|
| **init-app-dirs** | aipaas-init-app-dirs | — | — | 一次性初始化：预创建应用日志目录 |
| **postgres** | aipaas-postgres | 5432 | 5432 | Nacos 主库 |
| **redis** | aipaas-redis | 6379 | 6379 | 缓存 |
| **nacos** | aipaas-nacos | 8848 / 9848 | 8848 / 9848 | 配置中心 + 注册中心 |
| **rocketmq-namesrv** | aipaas-rocketmq-namesrv | 9876 | 9876 | RocketMQ 名称服务 |
| **rocketmq-broker** | aipaas-rocketmq-broker | 10911 / 10909 | 10911 / 10909 | RocketMQ 消息代理 |
| **svc-ingest** | aipaas-svc-ingest | 8000 | 8000 | 文档导入 / 入库服务（Python）|
| **svc-query** | aipaas-svc-query | 8001 | 8001 | 用户查询 / RAG 服务（Python）|
| **frontend** | aipaas-frontend | 80 | 80 | Nginx 托管的 React 前端 |

> **Java 微服务（javaplat）暂为规划状态**，未纳入编排（5 个 Dockerfile 已删除），模块规划与落地步骤见 `javaplat/TODO说明.md`。

### 2.2 模块依赖图（文字描述）

```
层 0 ──── 一次性初始化 ──── init-volumes（base：预创建中间件数据目录）
          │                 init-app-dirs（主编排：预创建应用日志目录）
          │
层 1 ──── 基础中间件（base）─── etcd ──────────┐
          │                 minio ────────────┤
          │                 mongodb ──────────┤
          │                 postgres ─────────┤
          │                                    │
层 2 ──── 依赖中间件的组件 ──── milvus ←─ etcd + minio
          │                 rocketmq-namesrv
          │                                    │
层 3 ──── 依赖层 2 的组件 ──── attu ←─ milvus
          │                 nacos ←─ postgres
          │                 rocketmq-broker ←─ rocketmq-namesrv
          │                                    │
层 4 ──── Python 服务 ──── svc-ingest ←─ milvus + minio + mongodb + init-app-dirs
          │                 svc-query  ←─ milvus + minio + init-app-dirs
          │                                    │
层 5 ──── 前端 ──── frontend ←─ svc-ingest + svc-query
```

启动顺序总结：`init-volumes / init-app-dirs → etcd/minio/mongodb/postgres → milvus → attu/nacos/rocketmq-namesrv → rocketmq-broker → svc-ingest/svc-query → frontend`

所有服务都加入 `aipaas-network` 桥接网络（主编排顶层 `networks.default.name` 统一指定，优先级高于 include 的 base 文件），容器间通过 **服务名** 互相通信（如 `milvus:19530`、`nacos:8848`）。

> **profiles 机制已删除**：不再使用 `--profile middleware/python/java/web/all`，分层启动改用 `docker compose up -d <服务名>`（见第 5 节）。

| 端口 | 用途 | 占用者 |
|------|------|--------|
| 80 | 前端 Nginx | frontend |
| 19530 | Milvus gRPC | milvus |
| 9091 | Milvus metrics | milvus |
| 9000 / 9001 | MinIO API / Console | minio |
| 8848 / 9848 | Nacos HTTP / gRPC | nacos |
| 5432 | PostgreSQL | postgres |
| 6379 | Redis | redis |
| 27017 | MongoDB | mongodb |
| 9876 / 10911 / 10909 | RocketMQ | namesrv / broker |
| 3000 | Attu | attu |

# 批量检查以上端口是否被占用
for p in 80 19530 9091 9000 9001 8848 9848 5432 6379 27017 9876 10911 10909 3000 8000 8001; do
  ss -tlnp | grep -q ":$p " && echo "⚠️  端口 $p 已被占用" || echo "✅ 端口 $p 空闲"
done
```

## 4. 一键部署（docker compose up -d）

这是最简单的方式，适合首次部署或快速启动全部服务。

```bash
# 1. 进入部署目录
cd /coding/aipaas/deploy/docker

# 2. 拷贝环境变量模板，按需修改敏感配置（密码、Token、外部 LLM 地址等）
cp .env.example .env
vim .env

# 3. [可选] 加载辅助脚本，设置 HOST_UID/GID（避免数据卷权限问题）
#    如果不想用脚本，也可以手动编辑 .env 里的 HOST_UID/HOST_GID
source ../scripts/setup-env.sh
# 或指定环境：source ../scripts/setup-env.sh devhome

# 4. 一键启动全部服务（含 base 基础中间件 + 平台中间件 + Python 服务 + 前端）
docker compose up -d

# 5. 查看启动状态
docker compose ps
```

> **提示**：主编排通过 `include: docker-compose-base.yaml` 引入基础中间件，`docker compose up -d` 会一次性拉起合并后的全部 15 个服务。Docker Compose 会根据 `depends_on` 的 `condition: service_healthy` 声明，自动等待下层服务健康后再启动上层。
>
> **环境变量优先级**（高 → 低）：shell 已导出变量（`source ../scripts/setup-env.sh`）> `.env` 文件 > compose 文件内的内置默认值。

### 4.1 生产环境必改项

`.env` 中以下变量在生产部署时**务必修改**：

```bash
# MinIO 对象存储（与 setup-env.sh 命名一致）
MINIO_ACCESS_KEY=<改掉默认 minioadmin>
MINIO_SECRET_KEY=<强密码>

# MongoDB（base 编排中账密固定为 admin/123456，如需修改请同步改 docker-compose-base.yaml 与 MONGO_URL）
MONGO_URL=mongodb://admin:<强密码>@mongodb:27017/?authSource=admin

# PostgreSQL（Nacos 主库）
POSTGRES_PASSWORD=<强密码>

# Nacos 安全 Token（至少 32 字符随机字符串）
NACOS_AUTH_TOKEN=<用 openssl rand -base64 48 生成>

# 外部 LLM 服务地址和 API Key
# （代码实际读取 OPENAI_BASE_URL / OPENAI_API_KEY / MODEL，compose 已做 LLM_* → OPENAI_* 映射）
LLM_BASE_URL=https://your-llm-endpoint
LLM_API_KEY=<your-api-key>
```

### 4.2 镜像构建网络说明（`network: host`）

`docker-compose.yaml` 中 `svc-model-embedding` / `svc-model-reranker` 的 `build` 段声明了 `network: host`：

```yaml
build:
  context: ../../pymodules
  dockerfile: apps/model-embedding-worker/Dockerfile
  network: host
```

**作用域**：只影响 `docker compose build` 时构建容器内 `RUN` 步骤使用的网络，**不影响服务运行时的网络**。运行期所有服务仍接入 `aipaas-network`（bridge），通过 `svc-model-embedding:8003` 这类服务名互相访问。

**为什么需要 host 网络**

这两个镜像的 Python 依赖全部来自 torch 基座镜像，而基座构建需要从 PyTorch 官方源与 NVIDIA 分发的 CUDA wheel 下载大体积文件：

| 依赖 | 下载源 | 体积量级 |
|---|---|---|
| torch / torchvision / torchaudio（gpu 组） | `https://download.pytorch.org/whl/cu128` | 约 2.5 GB |
| `nvidia-*` CUDA 运行时（cublas / cudnn / cusparse 等） | PyPI（NVIDIA 官方包） | 约 3 GB |

Docker 默认 bridge 网络下，构建容器要经过 `docker0` 的 NAT 与 Docker 内置 DNS。对这类跨境大文件下载，典型表现是 TLS 握手长时间挂起、速率极低，最终触发 `UV_HTTP_TIMEOUT`（基座 Dockerfile 中设为 120s）而失败。改为 `network: host` 后，构建步骤直接复用宿主机的网卡、路由、DNS 与 MTU，绕开 NAT 层，下载可正常完成。

这也是**手动构建基座镜像时必须加 `--network host`** 的同一个原因：

```bash
cd /coding/aipaas/pymodules
docker build --network host --build-arg TORCH_VARIANT=cpu \
  -f docker/base/Dockerfile -t aipaas/aipaas-torch-cpu-base:local .
```

**为什么只有这两个服务声明**

| 服务 | 构建期联网内容 | 是否需 host 网络 |
|---|---|---|
| svc-model-embedding / svc-model-reranker | torch 基座依赖（PyTorch 官方源 + NVIDIA CUDA wheel） | 需要 |
| svc-ingest / svc-query | `uv sync` 不带 `--group`，不拉 torch；仅从阿里云/清华 PyPI 镜像取纯 Python 包 | 不需要 |
| frontend | 仅 `npm ci`，走 npm registry | 不需要 |

即：只有模型服务的依赖链会触达 `download.pytorch.org` 与 NVIDIA 的 CUDA wheel，这才是 bridge 网络下会卡死的部分；其余服务在 bridge 下可正常下载。

**注意事项**

1. 当前这两个 Dockerfile 自身只执行 `uv pip install --no-deps --no-build-isolation -e ...`（离线安装本地包），真正联网的是**基座镜像构建**。compose 中的 `network: host` 用于与该基座构建流程保持一致，并避免后续在 Dockerfile 中新增联网步骤时再次踩坑。
2. `network: host` 仅对 Linux 主机有实际意义（Docker Desktop 中 host 指向的是其内部虚拟机）。
3. 构建期使用 host 网络意味着构建容器不再与宿主机网络隔离，在共享构建机上需自行评估该风险。
4. 若宿主机通过代理访问外网，需显式传入 `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` 构建参数；host 网络不会自动继承 shell 中未导出的代理配置。

## 5. 按层部署（逐步启动）

如果只需要启动部分模块，或需要分阶段调试，可以按服务名逐层启动（profiles 机制已删除，不再使用 `--profile`；`up -d <服务名>` 会按 `depends_on` 自动拉起依赖链）。

### 5.1 分步操作

```bash
cd /coding/aipaas/deploy/docker

# 第 1 步：启动基础中间件（etcd, minio, milvus, attu, mongodb，来自 base 编排；
#          depends_on 会自动先跑 init-volumes 预创建数据目录）
docker compose up -d etcd minio milvus attu mongodb

# 第 2 步：启动平台中间件（postgres, redis, nacos, rocketmq，来自主编排）
docker compose up -d postgres redis nacos rocketmq-namesrv rocketmq-broker

# 第 3 步：启动 Python AI 服务（自动先跑 init-app-dirs 并等待 milvus/minio/mongodb healthy）
docker compose up -d svc-ingest svc-query

# 第 4 步：启动前端（等待 svc-ingest / svc-query healthy）
docker compose up -d frontend
```

### 5.2 或者一键全启

```bash
docker compose up -d
```

### 5.3 单独启动某个模块

```bash
# 只启动 Milvus 相关的中间件链（自动包含 init-volumes）
docker compose up -d milvus etcd minio

# 只启动 Python 查询服务（自动包含其依赖的中间件链）
docker compose up -d svc-query
```

### 5.4 停止 / 重启

```bash
# 停止全部
docker compose down

# 停止某个服务（保留容器）
docker compose stop svc-query

# 重启某个服务
docker compose restart svc-query

# 停止并删除容器 + 网络（保留数据卷）
docker compose down

# 停止并删除一切（⚠️ 会删除数据库数据！）
docker compose down -v
```

## 7. 常用运维命令

### 7.1 启停单服务

```bash
# 启动 / 重启
docker compose up -d svc-query
docker compose restart svc-query

# 停止
docker compose stop svc-query

# 停止并删除容器
docker compose rm -s -f svc-query
```

### 7.2 查看日志

```bash
# 查看某服务最近 100 行日志
docker compose logs --tail=100 svc-query

# 实时跟踪某服务日志
docker compose logs -f svc-query

# 跟踪多个服务
docker compose logs -f svc-query svc-ingest

# 查看全部服务日志（最近 50 行）
docker compose logs --tail=50
```

> **提示**：Docker 日志驱动配置了 `max-size: 50m, max-file: 3`，单个容器最多保留 3 个 50MB 日志文件（总计 150MB），超过后自动轮转。

### 7.3 进入容器调试

```bash
# 进入 Python 服务容器
docker exec -it aipaas-svc-query /bin/bash

# 进入 Postgres 用 psql 查询
docker exec -it aipaas-postgres psql -U nacos -d nacos
```

### 7.4 清理数据卷

⚠️ 以下操作**不可逆**，请确认数据已备份。

```bash
# 停掉所有容器
docker compose down

# 删除平台中间件命名卷（卷名前缀 = compose 项目名，默认为目录名 docker）
docker volume rm docker_pg-data docker_redis-data docker_nacos-data \
  docker_rocketmq-namesrv-data docker_rocketmq-broker-data

# 删除中间件数据目录（base 编排 bind mount 到 ${DOCKER_VOLUME_DIRECTORY}/volumes）
rm -rf "${DOCKER_VOLUME_DIRECTORY:-/home/aipaas/docker_hub}/volumes"

# 删除应用日志目录（如果 DOCKER_LOG_DIRECTORY 用了默认相对路径）
rm -rf logs/

# 重建 + 重启
docker compose up -d
```

### 7.5 重建镜像

当 Dockerfile 或源码有变更时：

```bash
# 只重建 Python 服务镜像
docker compose build svc-ingest svc-query

# 只重建前端镜像
docker compose build frontend

# 重建全部
docker compose build

# 重建后重启对应服务
docker compose up -d svc-ingest svc-query
```

> **模型服务镜像的前提**：`svc-model-embedding` / `svc-model-reranker` 的 Dockerfile 以 torch 基座镜像为 `FROM`，`docker compose build` 只会叠加业务代码，**不会自动构建基座**。以下情况需先手动重建基座（必须带 `--network host`，原因见 [4.2](#42-镜像构建网络说明network-host)）：
>
> - 首次部署，本地还没有 `aipaas/aipaas-torch-{cpu|gpu}-base:local`
> - `pymodules/uv.lock` 或 `pymodules/pyproject.toml` 变更（基座内记录了 lock 指纹，不一致时子镜像构建会直接失败）
> - 切换 `TORCH_VARIANT`（cpu ↔ gpu），两个变体是两个独立镜像
>
> ```bash
> cd /coding/aipaas/pymodules
> docker build --network host --build-arg TORCH_VARIANT=cpu \
>   -f docker/base/Dockerfile -t aipaas/aipaas-torch-cpu-base:local .
> # 再回到 deploy/docker 重建模型服务镜像
> cd /coding/aipaas/deploy/docker && docker compose build svc-model-embedding svc-model-reranker
> ```

> **前端手动构建**（不走 compose）：
>
> ```bash
> cd /coding/aipaas/web
> docker build -t aipaas/frontend:latest .
> ```
>
> 前端 Dockerfile 只跑 `npm ci` + `vite build`，从 npm registry 取包，**不需要 `--network host`**（不需要 torch / NVIDIA CUDA wheel）。构建产物体积小（~7 MB），首次无缓存时整体耗时约 1 分钟。

### 7.6 构建常见错误排查

#### 错误 0：`vite: not found`（前端构建最常见坑）

```
Step 7/7 : RUN npm run build
 > aipaas-frontend@0.1.0 build
 > vite build
sh: vite: not found
```

**根因**：宿主 `node_modules` 被 `COPY . .` 覆盖进容器。Dockerfile 的层顺序原本是：

```dockerfile
RUN npm ci                              # ① 装依赖（含 vite）到 /app/node_modules
COPY . .                                # ② 把宿主所有文件拷到容器
RUN npm run build                       # ③ vite 执行
```

如果宿主有 `node_modules/`（可能只装了 dependencies 没装 devDependencies、或宿主是 glibc 容器是 musl），且没有 `.dockerignore` 排除它，**第 ② 步会把宿主的 node_modules 合并进容器的 node_modules**。Docker COPY 对目录是"合并"，不是"替换"——宿主 node_modules 里的文件会覆盖容器同名文件。如果宿主没 vite（只装了 dependencies），容器的 vite 就被覆盖丢失。

更糟糕的是 **`mv` 陷阱**：如果用 `mv /app/.hidden_node_modules /app/node_modules` 想保护依赖，当 `/app/node_modules` 已存在（宿主带进来的），`mv` 不会替换它，而是把 `.hidden_node_modules` 挪到 `/app/node_modules/.hidden_node_modules` 里，依赖被埋了一层，看起来成功其实 npm run build 用的还是宿主坏版本。

**本项目已修复**：[web/Dockerfile](file:///coding/aipaas/web/Dockerfile#L33-L50) 现在的顺序：

```dockerfile
RUN npm ci                              # ① 装依赖
RUN mv /app/node_modules /app/.container-node_modules   # ② 立刻挪走，避开 COPY
COPY . .                                # ③ 宿主文件进来，不影响 .container-node_modules
RUN rm -rf /app/node_modules \          # ④ 删掉宿主可能带进来的坏 node_modules
 && mv /app/.container-node_modules /app/node_modules \  # ⑤ 把好的挪回来
    || npm ci                           #    兜底：如果 .container-node_modules 丢了
 && npm run build                       # ⑥ 构建
```

这个方案**无论宿主有没有 `.dockerignore`、宿主 node_modules 是好/坏/不存在**，都能保证容器用自己的干净依赖。

**解决你当前机器上的问题**（如果你遇到了）：

```bash
cd /coding/aipaas/web
# 1. 确保拿到最新的 Dockerfile 和 .dockerignore
git pull                               # 或手动同步文件
# 2. 清理旧缓存（关键！旧缓存里可能有污染的 COPY . . 层）
docker builder prune -af               # buildkit
docker system prune -af                # legacy
# 3. 重新构建
docker build -t aipaas/frontend:latest .
```

#### 错误 1：`npm ci` 报错 `lockfile has changed`

```
npm ERR! code EUSAGE
npm ERR! npm ci can only install with an existing package-lock.json...
```

**原因**：`npm ci` 要求 `package.json` 与 `package-lock.json` 严格匹配。若 `package.json` 加了新依赖但没 `npm install` 生成 lock 更新，`npm ci` 会直接失败（这是 `npm ci` 的刻意设计，避免构建时偷偷改 lock）。

**解决**：在宿主机先同步一次：

```bash
cd /coding/aipaas/web
npm install      # 更新 package-lock.json
docker build -t aipaas/frontend:latest .
```

#### 错误 2：`printf: %/ ... invalid format`（或类似 `printf` 报错）

```
sh: %/...: invalid format
```

**原因**：Dockerfile 中若用 `printf` 把脚本写到容器里，格式串里的 `%` 会被 printf 当成格式说明符。比如想输出 bash 参数替换 `${var%/}`（最短匹配去尾斜杠），必须写成 `printf '...%%/...'` —— printf 里 `%%` 才输出字面量 `%`，`%%/` 才输出 `%/`。

本项目前端 Dockerfile 已用正确的 `%%/` 写法。若你在自己的 Dockerfile 里遇到，把脚本直接写成独立文件 COPY 进去比 printf 拼字符串更不容易踩坑。

#### 错误 3：`npm ci` 卡在 `fetch` 或超时

```
npm ERR! network request to https://registry.npmjs.org/... failed
```

**原因**：Docker 构建容器走 bridge 网络访问 npm registry 超时（类似 torch 基座访问 download.pytorch.org 的问题）。但与 torch 不同，npm registry 在国内通常有镜像可切。

**解决**（二选一）：

```bash
# 方案 A：给构建容器加 host 网络（和模型服务一样）
cd /coding/aipaas/web && docker build --network host -t aipaas/frontend:latest .

# 方案 B：在 Dockerfile 里把 npm registry 切到国内镜像（推荐，无需每次手动加参数）
# 在 "RUN npm ci" 之前加一行：
RUN npm config set registry https://registry.npmmirror.com
```

#### 错误 4：容器启动即退出，日志 `nginx: [emerg] host not found in upstream`

```
2025/xx/xx [emerg] 1#1: host not found in upstream "aipaas-aiworld.com"
```

**原因**：nginx 在 `proxy_pass http://<域名>/` 里写死了域名，容器启动时 nginx 会同步解析该域名。若此时 compose 网络的 DNS 还没就绪（比如依赖的后端服务还没起来），解析失败 → nginx 直接退出容器。

**本项目已解决**：`nginx.conf.template` 用 `resolver 127.0.0.11` + `proxy_pass $query_upstream`（变量 + set 语句），把 DNS 解析推迟到**请求时**而不是**启动时**，容器可以先正常启动。若你在其他 nginx 配置里遇到同样问题，照这个模式改。

## 8. 日志管理

### 8.1 架构说明

AIPaaS 采用**双层日志**策略：

1. **容器标准输出**（stdout/stderr）—— 由 Docker 日志驱动管理，轮转策略为 `max-size: 50m, max-file: 3`
2. **应用文件日志** —— 各服务进程内部写入 `/app/logs` 目录，统一挂载到宿主机 `${DOCKER_LOG_DIRECTORY}`

### 8.2 宿主机日志目录结构

默认情况下（`.env` 中 `DOCKER_LOG_DIRECTORY=.`），日志位于 `deploy/docker/logs/`：

```
${DOCKER_LOG_DIRECTORY}/logs/
├── svc-ingest/
└── svc-query/
```

各服务独立子目录，互不干扰。目录由主编排的 `init-app-dirs` 一次性容器预创建并统一属主。

### 8.3 Docker 日志驱动配置（docker-compose.yaml 中统一声明）

```yaml
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "50m"     # 单个日志文件最大 50MB
    max-file: "3"       # 最多保留 3 个文件
    tag: "{{.Name}}/{{.ID}}"

# 每个服务通过 YAML 锚点继承
services:
  svc-query:
    <<: [*default-logging]
    ...
```

### 8.4 修改日志级别

编辑 `.env` 中的 `LOG_LEVEL`：

```bash
# 可选：DEBUG / INFO / WARNING / ERROR
LOG_LEVEL=DEBUG
```

修改后重启相关服务生效：

```bash
docker compose restart svc-query svc-ingest
```

### 8.5 修改日志目录

编辑 `.env` 中的 `DOCKER_LOG_DIRECTORY`：

```bash
# 绝对路径示例
DOCKER_LOG_DIRECTORY=/data/aipaas/logs

# 或继续用相对路径
DOCKER_LOG_DIRECTORY=./logs
```

修改后需要重新 `docker compose up -d` 生效（数据卷挂载变更需要重建容器）。

## 9. 新增模块接入规范

> 新增服务需严格遵循以下规范，确保与现有体系无缝集成。

### 9.1 目录放置位置

根据技术栈选择放置目录：

| 技术栈 | 源码目录 | Dockerfile 位置 | build context |
|--------|---------|----------------|---------------|
| Python AI 服务 | `pymodules/apps/<svc-name>/` | `pymodules/apps/<svc-name>/Dockerfile` | `../../pymodules` |
| Java 微服务 | `javaplat/<svc-name>/` | **暂缓**：先评审 `javaplat/TODO说明.md`，落地后再定 Dockerfile 与 build context | — |
| 前端 | `web/` | `web/Dockerfile` | `../../web` |

### 9.2 Dockerfile 规范

```dockerfile
# =============================================================================
# 示例：Python 服务 Dockerfile
# =============================================================================

# 1. 基础镜像：Python 用官方 slim，Java 用 eclipse-temurin:21-jre
FROM python:3.12-slim AS runtime

# 2. 设置工作目录
WORKDIR /app

# 3. 安装依赖（利用 Docker 层缓存，先拷依赖声明）
COPY pyproject.toml uv.lock ./
RUN pip install uv && uv sync --frozen --no-dev

# 4. 拷贝源码
COPY . .

# 5. 创建日志目录
RUN mkdir -p /app/logs

# 6. 声明卷（与 docker-compose.yaml 中 VOLUME 挂载一致）
VOLUME ["/app/logs"]

# 7. 暴露端口（EXPOSE 仅文档作用，实际端口映射在 compose 里）
EXPOSE 8000

# 8. 健康检查（必须实现！）
HEALTHCHECK --interval=30s --timeout=5s --retries=3 --start-period=30s \
  CMD .venv/bin/python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"

# 9. 启动命令
CMD [".venv/bin/python", "-m", "uvicorn", "your_module.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Java 服务 Dockerfile **暂缓落地**（规划中的统一模板约定：`eclipse-temurin:21-jre-alpine` 运行 jar、`VOLUME ["/app/logs"]`、日志文件名用 `LOG_FILE_PREFIX=<模块名>`、健康检查 `/actuator/health`）。评审通过后按 `javaplat/TODO说明.md` 第 3 节的落地步骤补充，本文档与第 9.3 节模板届时同步更新。

### 9.3 docker-compose.yaml 添加服务模板

在主编排对应层的位置追加：

```yaml
  # ---------- svc-xxx（简要说明） ----------
  svc-xxx:
    build:
      context: ../../pymodules        # Java 服务落地后改为 ../../javaplat（待实现）
      dockerfile: apps/xxx-worker/Dockerfile
    image: aipaas/svc-xxx:latest
    container_name: aipaas-svc-xxx
    env_file: .env
    environment:
      # 内部服务地址用容器名（在 aipaas-network 内直接用）
      NACOS_HOST: nacos
      NACOS_PORT: "8848"
      TZ: Asia/Shanghai
    ports:
      - "${XXX_PORT:-8090}:8090"
    volumes:
      # 日志挂载，与 init-app-dirs 容器预创建目录对应
      - ${DOCKER_LOG_DIRECTORY:-.}/logs/svc-xxx:/app/logs
    healthcheck:
      test: ["CMD-SHELL", "wget -q -O- http://localhost:8090/actuator/health || exit 1"]
      interval: 30s
      timeout: 5s
      retries: 5
      start_period: 60s
    depends_on:
      # 用 condition: service_healthy 确保依赖先就绪
      nacos:
        condition: service_healthy
      postgres:
        condition: service_healthy
    # 复用全局锚点（日志 / 重启策略）
    <<: [*default-restart, *default-logging]
```

**关键点说明**：

| 配置项 | 要求 |
|--------|------|
| `container_name` | 统一命名：`aipaas-<service-name>` |
| `env_file` | 所有 Java / Python 服务必须加载 `.env` |
| `environment` | 中间件地址写**容器名**（如 `milvus`、`nacos`），不要写 `localhost` |
| `volumes` | 日志目录必须挂载到 `${DOCKER_LOG_DIRECTORY}/logs/<service-name>:/app/logs` |
| `healthcheck` | **必须**实现，且检查端口 / 路径与服务实际一致 |
| `depends_on` | 必须用 `condition: service_healthy`，不要用隐式依赖顺序 |
| `<<` YAML 锚点 | 必须继承 `*default-logging`、`*default-restart` |
| `networks` | 无需声明，服务自动加入顶层 `networks.default` 指定的 `aipaas-network`（主编排优先级高于 include 的 base 文件），**不要**自行定义新网络 |

### 9.4 .env.example 新增变量

如果新服务需要新的端口或配置变量，在 `.env.example` 对应段落追加：

```bash
# =============================================================================
# 新增服务端口变量（示例）
# =============================================================================

# --- XXX 服务 ---
XXX_PORT=8090
XXX_SOME_OTHER_VAR=default_value
```

### 9.5 init-app-dirs 预创建日志目录

在主编排 `docker-compose.yaml` 的 `init-app-dirs` 服务 `command` 中的 `mkdir -p /logs/...` 列表里加上新服务的日志子目录：

```yaml
command: >
  sh -c "mkdir -p /logs/svc-ingest /logs/svc-query ... /logs/svc-xxx    ← 新增
    && chown -R ${HOST_UID:-1000}:${HOST_GID:-1000} /logs"
```

（base 编排的 `init-volumes` 负责中间件数据目录，一般无需改动。）

这样首次部署时日志目录会被自动创建并设置好权限。

### 9.6 健康检查要求

| 技术栈 | 必须实现的端点 | 说明 |
|--------|---------------|------|
| **Python（FastAPI）** | `GET /health` | 返回 200 OK 即健康。可同时在返回体中包含依赖检查结果。 |
| **Java（Spring Boot）** | `GET /actuator/health` | 引入 `spring-boot-starter-actuator` 依赖，默认提供。可按需配置 `management.endpoints.web.exposure.include=health,info`。 |
| **前端（Nginx）** | `GET /health` | 在 `nginx.conf.template` 中加一行 `location /health { return 200 'ok'; }` |

### 9.7 网络互通

所有服务自动加入顶层 `networks.default` 指定的 `aipaas-network` 桥接网络（主编排的顶层网络配置优先级高于 include 的 base 文件）。

**通信规则**：
- 容器之间 → 用 **服务名** 或 **container_name** 直接访问（如 `http://milvus:19530`、`postgres:5432`）
- 容器访问宿主机本机服务 → 用 `host.docker.internal`（Linux 上需确保 Docker 版本 ≥ 24 或手动添加 `extra_hosts`）
- 宿主机访问容器 → 用 `localhost:<映射端口>`

新服务接入后，按以下清单逐项验证：

- [ ] Dockerfile 能成功构建（`docker compose build svc-xxx`）
- [ ] docker compose config 校验通过（见第 10 节）
- [ ] 服务容器启动成功，`docker compose ps` 状态为 healthy
- [ ] 健康检查端点返回 200 OK
- [ ] 日志输出正常（stdout 和 /app/logs 文件日志）
- [ ] 能正确连接所有依赖的中间件（在容器内用 `curl` / `ping` 验证）
- [ ] 网络互通：用容器名访问其他服务
- [ ] 从宿主机 `curl localhost:<映射端口>/health` 可访问
- [ ] 一键 `docker compose up -d` 时能随依赖自动拉起它
- [ ] `.env.example` 新增变量有默认值且文档注释清晰

## 10. 常见问题排查

### 10.1 docker compose config 校验

这是**排障第一步**——能定位 YAML 语法错误、变量替换问题：

```bash
cd /coding/aipaas/deploy/docker
docker compose config
```

期望：输出完整的合并后 YAML，无报错。如果有错误提示，根据提示修正 `.env` 或 `docker-compose.yaml`。

检查某个服务是否正确合并：

```bash
docker compose config | grep -A 50 "svc-query:"
```

### 10.2 端口冲突

**症状**：`docker compose up -d` 报错 `bind: address already in use`。

**排查**：

```bash
# 找到被占用的端口 & 占用进程
ss -tlnp | grep <端口号>
# 或
lsof -i :<端口号>

# 查看是不是旧的容器没停
docker ps -a | grep -i aipaas
docker rm -f <旧容器名>
```

**解决**：
- 如果是其他进程占用 → 停掉它，或在 `.env` 里改对应端口映射
- 如果是 Docker 容器残留 → `docker compose down` 清理

### 10.3 数据卷权限问题

**症状**：容器日志出现 `Permission denied`、`chown: operation not permitted`、数据库无法写入数据卷。

**排查 & 解决**：

```bash
# 查看当前用户 uid/gid
id

# 方案一：用 setup-env.sh 自动同步
source ../scripts/setup-env.sh

# 方案二：手动设置 HOST_UID / HOST_GID 到 .env
export HOST_UID=$(id -u)
export HOST_GID=$(id -g)
sed -i "s/^HOST_UID=.*/HOST_UID=$HOST_UID/" .env
sed -i "s/^HOST_GID=.*/HOST_GID=$HOST_GID/" .env

# 清理旧数据并重新初始化
docker compose down
rm -rf "${DOCKER_VOLUME_DIRECTORY:-/home/aipaas/docker_hub}/volumes" logs/
docker compose up -d init-volumes init-app-dirs
docker compose up -d
```

### 10.4 服务卡在 starting 或 unhealthy

**症状**：`docker compose ps` 显示 `starting` 很久，或 `unhealthy`。

**排查步骤**：

```bash
# 1. 看该服务的完整启动日志
docker compose logs --tail=200 <服务名>

# 2. 看依赖链上一级是否 healthy（depends_on condition 是否满足）
docker compose ps <依赖服务名>

# 3. 手动在容器内跑健康检查命令
docker exec -it <容器名> /bin/bash
# 然后执行 healthcheck 里的命令，看输出

# 4. 确认中间件地址是否写对（容器名 vs localhost）
#    容器间应该用服务名，比如 milvus:19530，不是 localhost:19530
docker exec -it <容器名> sh -c "wget -q -O- http://milvus:19530 || echo 'milvus 不通'"
docker exec -it <容器名> sh -c "wget -q -O- http://nacos:8848 || echo 'nacos 不通'"
```

### 10.5 容器间网络不通

**排查**：

```bash
# 确认两个容器都在 aipaas-network 里
docker network inspect aipaas-network

# 在容器内 ping 服务名（需要容器有 ping）
docker exec -it aipaas-svc-query sh -c "wget -q -O- http://milvus:19530"

# 直接用容器 IP 测
docker exec -it aipaas-svc-query sh -c "wget -q -O- http://$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' milvus-standalone):19530"
```

**常见原因**：
- 新服务自行定义了网络、未使用顶层默认网络 → 没有加入 `aipaas-network`
- 服务名写错（注意 `container_name` 与 `services:` 下的 key 不一样时的影响）
- 中间件用的宿主机 IP 被墙或防火墙拦截

### 10.6 LLM 模型连不上

**症状**：Python 服务日志出现 LLM 请求超时或 Connection Refused。

**排查**：

```bash
# LLM 如果跑在宿主机，确认 host.docker.internal 可达
docker exec -it aipaas-svc-query sh -c "wget -q -O- http://host.docker.internal:11434/api/tags"

# 如果上面不行，查一下实际 IP
docker run --rm alpine sh -c "getent hosts host.docker.internal"

# Linux 旧版 Docker 可能不支持 host.docker.internal，需要手动改
# 在 docker-compose.yaml 的 svc-ingest / svc-query 服务里加：
# extra_hosts:
#   - "host.docker.internal:host-gateway"
```

或者直接在 `.env` 里把 `LLM_BASE_URL` 改成宿主机真实 IP：

```bash
# 宿主机上执行取本机 IP
ip route | grep default | awk '{print $3}'
# 然后把 LLM_BASE_URL 改成 http://<那个IP>:11434
```

### 10.7 Nacos 数据库初始化失败

**症状**：Nacos 容器反复重启，日志里有 `Failed to start server` 或 PostgreSQL 连接错误。

**排查**：

```bash
# 看 Nacos 日志
docker compose logs --tail=200 nacos | grep -i "postgresql\|error\|fail"

# 确认 PostgreSQL 已 healthy、可连接
docker exec aipaas-postgres pg_isready -U nacos

# 如果数据库数据坏了，清空命名卷重建（⚠️ Nacos 配置数据会丢）
docker compose down
docker volume rm docker_pg-data
docker compose up -d postgres
# 等 postgres healthy 后再起 nacos
docker compose up -d nacos
```

### 10.8 Milvus 启动极慢或 OOM

**症状**：Milvus 卡在 starting 很久（start_period 设置的 120 秒还不够），或被 OOM Killer 杀掉。

**排查**：

```bash
# 看主机内存，Milvus 启动需要足够 RAM
free -h

# Milvus 日志
docker compose logs --tail=100 milvus

# 如果资源紧张，考虑换轻量模式（当前已用 standalone）
# 或者加大宿主机内存
```

**临时缓解**：在 `.env` 中降低 JVM 参数（仅对 Nacos / RocketMQ 有效），Milvus 自身的内存需要在宿主机层面保证。

### 10.9 前端 Nginx 反向代理不通后端

**症状**：前端页面能打开，但 API 请求 502 Bad Gateway。

**排查**：

```bash
# 查看前端容器内的 nginx.conf
docker exec -it aipaas-frontend cat /etc/nginx/nginx.conf
# 确认 QUERY_API_UPSTREAM 和 IMPORT_API_UPSTREAM 渲染为正确的服务名

# 在前端容器内直接 curl 后端
docker exec -it aipaas-frontend sh -c "wget -q -O- http://svc-query:8001/health"
docker exec -it aipaas-frontend sh -c "wget -q -O- http://svc-ingest:8000/health"

# 后端如果没启动 → docker compose up -d svc-query svc-ingest
```

### 10.10 快速恢复：一键重置全部

当你想彻底清掉重来时：

```bash
cd /coding/aipaas/deploy/docker

# 停掉一切，删除容器 + 网络 + 数据卷（⚠️ 数据会丢）
docker compose down -v

# 清理镜像（可选，会触发下次重新 build）
docker compose build --no-cache

# 重建
docker compose up -d
```
