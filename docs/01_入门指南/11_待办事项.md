## 三、当前项目问题汇总

### 1. 架构层面

- **服务拆分过散**：导入服务（8000）与查询服务（8001）是两个独立 FastAPI 应用，前端需要跨端口请求，无法走同源/统一网关；建议合并为单应用或加统一 API 网关（Nginx）。
- **任务状态仅存内存**（`task_utils.py` 字典）：服务重启后任务状态全部丢失，无法恢复轮询，也无法实现"任务列表"接口；建议持久化到 Redis/MongoDB。
- **`allow_origins=["*"]` + `allow_credentials=True`**：CORS 配置组合不安全且部分浏览器会拒绝；上线前必须收敛为白名单。
- **无鉴权体系**：所有接口裸奔，session_id 由前端 localStorage 自造，任何人可伪造/读取他人会话历史。

### 2. 后端接口设计

- **会话无标题/无列表**：Mongo 中仅按 `session_id` 存消息，没有会话元数据表，导致对话历史列表（侧边栏）无法由后端支撑。
- **`session_id` 与用户无绑定**：清空历史、查询历史均未校验归属。
- **`POST /query` 流式模式**：先返回 `session_id` 再由前端连 `/stream/{session_id}`，两步之间存在竞态（图已开始推送，SSE 尚未建立时的事件会丢失）。
- **非流式 `/query` 同步阻塞**：`run_query_graph` 在请求线程内同步执行，长查询会阻塞 worker。
- **任务失败原因未返回**：`/status` 只返回 `failed` 状态，没有 error message 字段。
- **无分页/游标**：`/history` 仅支持 limit，无 offset/cursor。

### 3. 前端旧版页面（`pymodules/app/rag/pages/`）

- `API_BASE` 硬编码 `http://127.0.0.1:8001`，且导入页用 `/` 同源，两页配置不一致。
- 上传进度条为**模拟进度**（直接写 50%），与真实上传无关。
- 轮询间隔写死（1.2s / 2s），无退避、无终止上限。
- `confirm()` / `alert()` 原生弹窗体验差。
- 无登录态、无路由，页面间跳转依赖后端静态路由。

### 4. 工程与规范

- 前端无独立工程（旧版 HTML 内嵌 JS/CSS），无构建、无组件化、无类型检查；本次 React 重构已解决，但需补充 ESLint/Prettier/单元测试。
- 前后端接口契约无统一文档（仅有 FastAPI 自动 docs），建议维护 OpenAPI 规范 + 前端 codegen。
- `frontend/` 与后端静态页面并存期间，需明确 Nginx/网关的路由分工（React 走 `/`，旧页面走 `/legacy/`）。
- 环境变量管理缺失：API 地址应通过 `.env`（`VITE_API_BASE`）配置，禁止硬编码。

### 5. 安全

- 文件上传未校验大小上限、MIME 白名单与文件名清洗（存在路径穿越风险：`local_dir_obj / file.filename`）。
- MinIO 桶名等配置需确认非公开读写。
- 无登录限流/防爆破，无接口级鉴权中间件（JWT 校验）。
