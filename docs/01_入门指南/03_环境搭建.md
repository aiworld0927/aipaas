# 开发环境搭建

本文档面向 **AIPaaS Python AI 服务（`pymodules/`）**、**Java 网关与管理平台（`javaplat/`）**、**React 前端（`web/`）** 的日常开发与测试。五级容器编排见 [guides/02a_总体部署手册.md](04_总体部署手册.md)；快速使用入口见 [guides/00_快速使用入门.md](01_快速使用入门.md)。

## 1. 前置要求

| 依赖 | 版本 | 说明 |
| --- | --- | --- |
| Python | 3.12 | 由 `pymodules/.python-version` 固定，uv 会自动下载 |
| uv | 0.13+ | Python workspace 统一的依赖管理与虚拟环境工具 |
| JDK | 21 | Java 网关与管理平台构建/运行 |
| Maven | 3.9+ | Java 多模块构建（推荐用仓库自带 `javaplat/mvnw`） |
| Node.js | 20+ | 前端构建（推荐 `nvm use 20`） |
| Docker / Docker Compose | 29+ | 启动五级容器编排、构建应用镜像 |
| NVIDIA GPU（可选） | CUDA 12.x | 需要本地跑嵌入/重排模型时使用；纯接口开发用 CPU 版即可 |

## 2. 工程结构

```
pymodules/
├── apps/        # 可独立部署的业务应用（workspace 成员）
│   ├── ingest-worker/    # svc-ingest，端口 8001
│   ├── query-worker/     # svc-query，端口 8002
│   ├── model-embedding-worker/   # svc-model-embedding，端口 8003
│   ├── model-reranker-worker/    # svc-model-reranker，端口 8004
│   ├── apis/             # 平台侧 API（未纳入 workspace，暂不处理）
│   └── eval-runner/      # 离线评测脚本（尚未适配，暂不可运行）
├── packages/    # 给 apps 提供的公共依赖（workspace 成员）
│   ├── common/           # 配置 / 日志 / 上下文 / 通用工具
│   ├── generation/       # LLM 生成封装
│   ├── model-clients/    # 嵌入 / 重排 / LLM HTTP 客户端
│   ├── nacos/            # Nacos 注册与服务发现
│   ├── pipeline/         # RAG 编排基类
│   ├── retrieval/        # Milvus 混合检索
│   ├── storage/          # MongoDB / MinIO
│   ├── mcp-agents1.0/    # query-worker 使用的 MCP 客户端
│   └── mcp-agents2.0/    # 独立管理，不在 workspace 中
├── configs/     # 配置与提示词（Compose 内挂为 /app/configs）
├── tests/       # 按场景组织的验证脚本（非 pytest）
├── scripts/acceptance/   # 可执行验收工具（P0 / 安全 / 性能 / golden）
├── pyproject.toml        # workspace 根：声明 members + cpu/gpu 互斥分组
└── uv.lock               # 全仓唯一锁文件
```

依赖方向为单向：`apps/* → packages/*`；`packages/*` 之间只允许 `common ← llm ← retrieval` 这类向下依赖，禁止反向依赖 `apps/*`。

仓库文档已按主题重组，入口见 [docs/README.md](../README.md)；架构专题文档集中在 [docs/02_架构设计/](../02_架构设计)（应用/数据/部署/技术/调用链），部署与验收在 [docs/03_运维验收/](../03_运维验收)。

### 为什么每个 `packages/*` 都要有独立 `pyproject.toml`

这是 **uv workspace 的硬性要求**：uv 通过成员目录中的 `pyproject.toml` 识别“这是一个独立的包”，并据此完成依赖解析、依赖图构建、editable 安装和按包构建。没有 `pyproject.toml` 的目录只是普通目录，不会被安装，`import aipaas_xxx` 会直接失败。

保留独立 `pyproject.toml` 的实际收益：

1. **依赖边界可校验**：`llm` 只能依赖 `common`，若有人误加 `pymilvus` 会体现在该包的依赖里，而不是悄悄混进全局。
2. **构建产物最小化**：容器镜像可按应用声明裁剪依赖，而不是把全部依赖塞进根项目。
3. **可单独构建发布**：`uv build --package aipaas-common` 可产出 wheel，便于后续私有源分发。
4. **依赖变更可审计**：新增依赖必须落到具体包，避免“根项目依赖膨胀”。

三种方案对比：

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 多包独立（**当前采用**） | `packages/*` 各一个 distribution | 边界清晰、可单独构建、依赖图准确 | 目录内多一个 `pyproject.toml` |
| 单根 `pyproject.toml` | `packages/` 仅作源码目录 | 文件更少 | 无法声明包间依赖，只能靠 `PYTHONPATH`，分层与裁剪全部失效 |
| 单包聚合 | 一个 `aipaas-shared` 包含全部模块 | 最简单 | 任何应用都会拖入全部依赖，包边界形同虚设 |

**结论**：`pyproject.toml` 必须保留；但每个包 **不需要** 独立的 `.venv`、`.python-version`、`uv.lock`、`Dockerfile` 或 `README.md`——这些统一由 `pymodules/` 根目录提供，所有成员共用同一个 `.venv`。

## 3. 首次初始化

```bash
cd pymodules
uv sync --all-packages
```

- 必须带 `--all-packages`：裸 `uv sync` 只安装根项目，而根项目不声明依赖，结果就是成员包和第三方库都没有装。
- 该命令会在 `pymodules/.venv` 中创建统一环境，并将 `apps/*`、`packages/*` 以 editable 方式安装。
- IDE（PyCharm / VS Code）的解释器请指向 `pymodules/.venv/bin/python`，不要为某个成员单独建环境。
- 校验锁文件与配置是否一致：

```bash
uv lock --check
```

## 4. 日常开发流程

### 4.1 启动服务

```bash
cd pymodules

# 查询服务 http://127.0.0.1:8002
uv run uvicorn query_worker.api.app:app --port 8002 --reload

# 导入服务 http://127.0.0.1:8001
uv run uvicorn ingest_worker.api.app:app --port 8001 --reload
```

只启动/调试某一个成员时，用 `--package` 指定成员（依赖解析范围仍来自同一 workspace）：

```bash
uv run --package svc-query uvicorn query_worker.api.app:app --port 8001
uv run --package svc-ingest python -m ingest_worker.graph.main
```

也可以先进入成员目录再执行，uv 会自动识别所属 workspace：

```bash
cd apps/query-worker
uv run python -m query_worker.graph.main_v2
```

### 4.2 依赖管理

所有依赖都必须声明在**成员**的 `pyproject.toml` 中，根项目不声明依赖。

```bash
cd pymodules

# 给某个包加/删依赖（推荐显式指定 --package，避免装到错误的项目）
uv add --package aipaas-retrieval elasticsearch>=8.0.0
uv remove --package aipaas-llm dashscope

# 修改后刷新锁文件并同步环境
uv lock
uv sync --all-packages
```

- `uv.lock` 由 uv 自动维护，**不要手工编辑**。
- 镜像源统一在根 `pyproject.toml` 的 `[[tool.uv.index]]` 配置，成员无需重复声明；例外是 PyTorch CPU 源，它在两个 `apps/*/pyproject.toml` 中单独声明。
- 包间依赖统一写成 workspace 引用：

```toml
[tool.uv.sources]
aipaas-common = { workspace = true }
```

### 4.3 新增一个共享包

1. 建目录：`packages/foo/aipaas_foo/__init__.py`
2. 新建 `packages/foo/pyproject.toml`（`name = "aipaas-foo"` + 依赖 + 下面三段）：

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["aipaas_foo"]
```

3. 加入根 [pyproject.toml](../../pymodules/pyproject.toml) 的 `members`；也可把 `members` 写成通配 `["apps/*", "packages/*"]`，新增包时无需再改根配置（`apps/apis` 无 `pyproject.toml`，不受影响）。
4. 在需要它的 `apps/*/pyproject.toml` 中加 `aipaas-foo` 依赖与 `{ workspace = true }` 源，然后 `uv lock && uv sync --all-packages`。

### 4.4 配置与提示词

- 全局配置：`pymodules/configs/aipaas_config.yaml`
- 提示词：`pymodules/configs/prompts/rag/*.prompt`，由 `aipaas_common.core.load_prompt` 加载
- 服务级环境变量：`apps/*/*/config.py`，通过 `python-dotenv` 读取 `.env`
- 中间件地址可复用 `deploy/scripts/setup-env.sh` 导出的变量

### 4.5 在应用包内新建并运行脚本

在 `apps/ingest-worker/ingest_worker/`（或 `apps/query-worker/query_worker/`）下新增脚本时，把它当作**包内模块**运行：

```bash
cd pymodules
uv run python -m ingest_worker.demo
```

之所以能这样跑：`uv sync` 已把 `apps/ingest-worker` 写入 `.venv` 的 editable 路径（`.venv/lib/python3.12/site-packages/_editable_impl_svc_ingest.pth`），因此 `ingest_worker` 在任何工作目录下都可导入。

四种可用写法（均已实际验证）：

```bash
# 1) 仓库根 + 模块名（推荐）
uv run python -m ingest_worker.demo

# 2) 应用目录 + 模块名
cd apps/ingest-worker && uv run python -m ingest_worker.demo

# 3) 直接指定文件路径
uv run python apps/ingest-worker/ingest_worker/demo.py

# 4) 显式限定 workspace 成员
uv run --package svc-ingest python -m ingest_worker.demo
```

`query_worker` 同理：`uv run python -m query_worker.demo`。

约定与注意：

- 脚本放在子目录（如 `ingest_worker/scripts/demo.py`）时用 `-m ingest_worker.scripts.demo`，并给 `scripts/` 补 `__init__.py`
- 文件名不要与标准库或第三方包同名（`json.py`、`types.py`、`logging.py`）
- 脚本需要中间件时先 `source deploy/scripts/setup-env.sh`
- IDE 调试：解释器选 `pymodules/.venv/bin/python`，工作目录选 `pymodules`，运行目标用 **Module name** 填 `ingest_worker.demo`（不要用 Script path）
- 顶层导入一律写 `ingest_worker.*`，不要写 `from graph...` / `from config...`
- 临时验证脚本用完即删，不要提交到 `ingest_worker/` 根目录

## 6. 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'langgraph'` / 任何第三方库 | 只执行了裸 `uv sync`，未安装成员依赖 | `uv sync --all-packages` |
| `ModuleNotFoundError: No module named 'graph'` 或导入了错误应用的 `graph` | 使用了顶层包名 `graph`/`api`，两个应用互相遮蔽 | 在应用内使用命名空间包 `ingest_worker.*` / `query_worker.*` |
| `ModuleNotFoundError: aipaas_common` | 成员未安装或未加入 workspace `members` | 检查 `members` 后 `uv lock && uv sync --all-packages` |
| `Invalid URL '/file-urls/batch': No scheme supplied` | 缺少 MinIO / 模型服务地址环境变量 | 先 `source deploy/scripts/setup-env.sh`，或在 `.env` 补齐地址 |
| IDE 中 import 全部标红 | 解释器指向了系统 Python | 切换为 `pymodules/.venv/bin/python` |
| `apps/eval-runner` 运行失败 | 仍在导入旧的 `app.agents.query_process` 路径 | 待适配为 `query_worker.*`，当前不可运行 |
| `apps/apis` 无法 import | 该目录未纳入 workspace | 按约定暂不处理 |

### A.5 GPU / CPU 双机器依赖分组

仓库根 `pymodules/pyproject.toml` 已内置互斥分组 `cpu` / `gpu`，两台机器共用同一份锁文件但各自只装自己那一组：

```bash
# 有 NVIDIA 显卡的机器（CUDA 12.8）
uv sync --all-packages --group gpu

# 只有 CPU 的机器
uv sync --all-packages --group cpu
```

校验版本：

```bash
uv run --no-sync python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
# GPU 期望：2.11.0+cu128 True
# CPU 期望：2.11.0+cpu  False
```

**三条不能踩的规则：**

1. 同步必须带 `--group`，裸 `uv sync` 会卸掉 torch。
2. 不要同时选两组，`uv` 会直接报错防止装出混杂环境。
3. 不要改 `pyproject.toml` 里 `flagembedding` 的位置——它**必须**在 `cpu` / `gpu` 两个分组里（经 accelerate / peft 强依赖 torch），留在通用依赖会导致默认依赖树额外解析出一个 PyPI 版 torch 把已有分组包覆盖掉。

### A.6 模型下载（离线部署时需要）

from modelscope.hub.snapshot_download import snapshot_download
# BGE-M3 嵌入模型

```

容器 `MODEL_BASE_DIR` 挂为宿主机 `/coding/models/BAAI`，镜像内读取 `bge-m3` / `bge-reranker-large` 子目录。

验证 CUDA 可用性：

uv run python -c "import torch; print('CUDA:', torch.cuda.is_available())"
```
